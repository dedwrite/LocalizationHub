# v0.7 Engine Compatibility Matrix (HONEST)

Status definitions (strict):

- **SUPPORTED** — a user can give LocalizationHub the raw format and extraction works end-to-end, validated against real files.
- **PARTIAL** — some valid variants work; documented limitations exist.
- **STRUCTURED-EXPORT ONLY** — LocalizationHub understands JSON/CSV produced by another tool but does not directly handle the original binary resource.
- **DETECTED ONLY** — the file is recognized but no extraction occurs.
- **EXTERNAL TOOL REQUIRED** — LocalizationHub can orchestrate a configured external dependency, but the binary parse itself is delegated.
- **OUT OF SCOPE** — intentionally not implemented.

This matrix reflects TESTED behavior, not desired architecture.

## What the first batch claimed vs. reality

The first batch overstated support: binary `.pak`/`.utoc`/`.pck`/`.assets` were
reported as "external tool" without any actual invocation; the LOCRES parser
used an incorrect layout. This revision:

- rewrote LOCRES/LOCMETA against the real format and validated them against real files;
- added the external-tool execution command and Tools/Dependencies config UI;
- wired automated orchestration: `Scan Game` now auto-invokes repak (`.pak`) and
  retoc (`.utoc`/`.ucas`) through isolated temp dirs and re-discovers/remaps the
  extracted resources to logical archive paths;
- added user-defined protected-token patterns (regex + label) registered under
  the `custom` token profile;
- left Godot `.pck` and Unity `.assets` binary archives as **EXTERNAL TOOL
  REQUIRED** until their CLI contracts are validated and a real end-to-end run
  against a genuine archive passes.

- Diagnostics were emitted **one per file** (88k cards).
- Engine detection gave LOW confidence despite thousands of Godot resources.
- The structured analyzer ignored common UI-text fields (`name`/`title`/

- **Resource classification** (`classifyFileKind`): CONTAINER / TEXT / SCRIPT /

- **Diagnostic aggregation**: repeated diagnostics collapse to one card with a

- **GDScript `.gd`** safe extraction (`tr` / `tr_n` / `TranslationServer.translate`).
- **Real PO/POT parser** (gettext).
- **UI-text field extraction** in the structured analyzer.
- **Engine detection**: project.godot or 100+ Godot resources → HIGH confidence.
- **Zero-entry safety**: a prominent `no-translatable-text` diagnostic when
  resources exist but nothing is extracted.
- **Stats**: `resourcesDiscovered` / `textResources` / `binaryResources` /
  `unsupportedResources` / `skipped` so "88k resources" is no longer conflated
  with "88k text candidates".

## Fifth batch — InkCPP `.inkb` story dialogue (Until Then primary story)

A deep investigation of the real `.inkb` corpus revealed it is **NOT upstream
InkCPP binary** — it is Until Then's custom serialization:

```
[10-byte header: u16=1, u32=20, u32=0]
<NUL-terminated strings>    ← metadata (type/characters/player), $ commands, dialogue
<binary command tail>       ← compiled Ink instructions (ignored)
```

Dialogue grammar (confirmed by the game's own `Constants.REGEX_DIALOGUE`):

```
char_key [ (duration) ] : text     → speaker line
:: text                            → inner thought (no speaker)
$ command                          → non-text
type: "..." / characters: {...} / player: "..." → metadata
```

Markers: `[.]`/`[..]` beats, `[$cmd]` inline commands, `[shake]/[wave]/…` BBCode,
`[:text]` click-to-reveal — all protected via the Godot token profile.

Real Until Then result:

| | Before | After |
|---|---|---|
| `.inkb` dialogue | 0 (DETECTED ONLY) | **16,414 entries** |
| Speaker coverage | — | **15,740 (96%)** |
| Engine | — | Godot **HIGH** |
| Story files parsed | 0 | **1,014 / 1,014** |
| Elapsed | — | ~150 ms |

Speaker identity: display name → character id via the `characters` header
(`"Mark" → "MarkBorja"`). Gender is **not** inferred (Until Then has no explicit
gender metadata → unknown). No C++ helper required — the format is parsed
natively in TypeScript.

Remaining honest limitations: `.translation` (keyless `OptimizedTranslation`),
binary `.res`/`.scn`/`.gdc` (GDRE conversion not wired).

## Sixth batch — Godot multi-locale normalization

The previous batch only validated `locales/ja`. A source-level audit confirmed a
real multi-locale bug in the **JSON databases** (the `.inkb` story corpus is
actually single-locale — see below).

### Universal culture aggregation (was Unreal-only)

`cultureAggregation.identityOf()` previously returned `undefined` for every
non-Unreal engine, so only LOCRES was ever aggregated. Replaced with a universal
interface: any entry carrying a `cultureIdentity` is grouped by it; Unreal falls
back to `target::namespace::key`. The source/native entry is selected via
`rawMetadata.isSourceLocale` (the unsuffixed base file) rather than alphabetical
order.

### JSON database multi-locale (real, fixed)

Until Then ships 8 copies of each database: `fb.json` (English base) +
`fb_ja/de/es/fil/fr/it/zh-CN.json`. Locale is detected from the filename suffix
(`detectGodotJsonLocale`), each entry carries `cultureIdentity = godot-db:<base>:<structural-path>`,
and the aggregator collapses them into ONE logical entry with `localeVariants`.

Real `databases/` result: **~25,000 raw → 3,408 logical entries**, 3,113 of them
multi-locale with **21,607 attached variants**; source = English (`en`, inferred
from the unsuffixed base content, overridable via the review's source selector).

### `.inkb` culture awareness (defensive)

`detectGodotInkbLocale` strips `locales/<culture>/` so the story identity is
culture-independent. **Reality check:** Until Then's recovered story corpus only
ships `ja` (1,014 unique files; the other ~5,500 `.inkb` are duplicate `ja`
copies in installer build artifacts). There are NO `fr`/`de`/`es` story files, so
cross-locale line matching is **not** exercised and remains unproven — the
`godot-inkb:<story>:<line>` identity is structural but not yet validated across
real locales.

## Seventh batch — story source discovery, full text coverage, language consistency

### Where the English story lives (runtime-proven)

`Story.gd` (`_get_story_inkb_file`) shows the exact locale-selection contract:

- `DEFAULT_LOCALE = "en"`, `BASE_STORY_DIR_PATH = "res://assets/story"`.
- English (default): `res://assets/story/<id>.inkb` — **no** locale prefix.
- Localized: `res://assets/story/locales/<locale>/<id>.inkb` (e.g. `ja`), with
  fallback to the base.

The recovered developer snapshot only contains `f/assets/story/locales/ja/` (the
Japanese overlay); the English base `.inkb` files are **absent** from it. So story
entries are correctly attributed `sourceLocale = "ja"` — the pipeline never
labels Japanese as English.

### Full `.inkb` text-section coverage (major fix)

A full audit of every NUL-terminated string across 1,014 story files revealed the
current regex only captured **explicit `char_key: text` lines**, missing **bare
continuation lines** — Until Then splits a speaker's speech across multiple
strings; only the first carries `char_key:`, the rest are bare and inherit the
previous speaker (also set by `$ F <char>` focus commands).

- Added speaker inheritance for bare lines → dialogue coverage **16,414 → 20,375
  entries** (+24%), with `continuation: true` metadata.
- Bare ASCII identifiers (`music_end`, `bgg75cdd4i5`) are story internals and are
  skipped, never treated as text.

### Choices

The NUL string section contains **0** `*` choice strings; Until Then's choices are native Ink choices surfaced via two command families:

- **`$ push_timed_choices <duration> <n>`** — timed player choices, immediately
  followed by parenthesized `(option)` strings until the next `$` command.
  **IMPLEMENTED**: the parser tracks the timed-choice block and emits each
  `(option)` as a `classification: 'Choice'` entry (`timedChoice: true`), never as
  narration continuation. Validated against the real corpus (`(Get it!)`,
  `(Run away!)`, 80 `push_timed_choices` commands).
- **`$ ftb.request_player_choice`** — followed by bare `left`/`middle`/`right`
  strings (pure-ASCII single tokens). **DETECTED ONLY**: these are structurally
  ambiguous (indistinguishable from narration or story internals), so they are
  skipped, not fabricated into choices. Documented boundary.


### Binary resources — moot for Until Then

The real game ships **0** binary `.res`/`.scn`/`.gdc` (Godot exports text
`.tscn`/`.gd` here). The GDRE conversion path remains DETECTED ONLY for other
games.

### Language consistency

Added `computeLocaleCoverage(entries)` and tests proving story=ja, DB=en, and no
cross-contamination; a `ja`-only story has no `en` variant (honest missing-locale
reality).

### Second independent Godot sample (Brotato)

Brotato is a Godot Mod Loader mod using **standard** Godot CSV localization
(`translations_ar.csv` with `keys,en,ar` columns), not Until Then's custom

Comparing the English base against each locale's structural fingerprint (the

| | Count |
|---|---|
| English base stories | 1,213 |
| **Structurally identical** | **1,139 (94%)** |

## Seventh batch — generic "Open File" context preservation

The extraction flow already carried rich `EntryContext`. This batch brings the
same explicit-context model to the ordinary **Open File** path (JSON / CSV /
PO / flat records), so opening a dialogue file no longer flattens it into only
`key + text`.

- New `ParsedDialogueContext` on `ParsedLocalizationEntry`: `speaker`,
  `speakerId`, `listener`, `listenerId`, `speakerGender`, `listenerGender`,
  `scene`, `conversationId`, `dialogueId`, `nodeId`, `choiceGroup`, `voice`,
  `portrait`, plus lossless `raw` values.
- Generic detector (`parsers/contextDetection.ts`) recognises explicit field
  names (speaker/talker/actor/character/from/sender, listener/addressee/
  recipient/target/to, speaker/listener gender + sex, scene, conversation,
  node, choice group, voice, portrait) and normalises genders via the shared
  vocabulary (`male`/`female`/`neutral`/`unknown`/`custom`) without ever
  guessing from names/language/prose.
- Nested `speaker: { id, name, gender }` objects and top-level
  `{ characters: {...}, dialogue: [...] }` databases resolve speaker/listener
  IDs to names/genders structurally.
- CSV: header-based context detection + BOM handling; PO: `# Speaker:`,
  `#. Listener Gender:` comment labels.
- Role-scoped gender is preserved separately (speaker vs listener); a bare
  `gender`/`sex` field is attributed to the speaker only when an explicit
  speaker field is also present.

`EntryContext` (extraction model) also gained `speakerPronouns`,
`listenerPronouns`, `previousEntryIds`/`nextEntryIds`, and a bare `voice` field.

Status: **SUPPORTED** for generic Open File context detection (unit-tested;
JSON nested/flat, CSV, PO, character-database resolution, no-guess guarantees).

Custom game schemas that use non-canonical field names (`char_from`,
`char_to`, `sex_a`, `sex_b`, `body`) are mapped through the **Context Mapping
review** — a `ContextFieldMapping` list (`fieldName` → `speaker`/`listener`/
`speakerGender`/`listenerGender`/`translatableText`/`ignore`) that flows into
the SAME `scanGame` pipeline the desktop "Apply & Rerun" button invokes. This
mapping contract is covered end-to-end at the pipeline level
(`genericContextMapping.test.ts`): `char_from`→speaker, `char_to`→listener,
`sex_a`→speakerGender, `sex_b`→listenerGender, `body`→source text, and the
negative case (no mapping → no fabricated context).

**Playwright coverage boundary (honest):** the Context Mapping review UI lives
in the desktop (Tauri) frontend and is driven by `invoke` IPC, which Playwright
does not exercise; the website app Playwright targets has no extraction/mapping
surface. The mapping contract is therefore verified at the core-pipeline level
above, not via a Playwright browser test of the desktop UI.

## Eighth batch — cross-engine finalization + deep-format characterization

### Godot deep formats (honest, evidence-based)

- **GDRE Tools v2.4.0** (built on Godot Engine 4.6 beta) is the verified local
  tool. Verified CLI (from `--headless` + invalid-flag help dump):

  (`godot-binary` job + guarded `copy_extraction_file`): copy → convert → parse

- **`.gdc` → text** — `--decompile=<FILE> --bytecode=<VERSION>` on a temp copy;
  requires the matching bytecode version. **SUPPORTED (derived copy)** when the
  bytecode version is known.
- **OptimizedTranslation (`.translation`)** — `--bin-to-txt` recovers the
  smaz-decompressed VALUES, but the `hash_table` is a `PackedInt32Array` of
  one-way StringName hashes; **keys are genuinely absent**. Key recovery needs
  `--recover --translation-hint=<candidates>` on the full project (hash-match

- **Until Then player Choices** — `$ push_timed_choices` timed choices are
  extracted from the NUL-string section as `Choice` entries (parenthesized
  `(option)` strings, validated against the real corpus). `$ ftb.request_player_choice`
  bare tokens (`left`/`middle`/`right`) are structurally ambiguous and remain
  **DETECTED ONLY** (documented boundary; no fabricated support).

runtime-visible engine/plugin stock strings (XeSS graphics-settings labels,
OnlineSubsystem presence/error text). These are shipped by the engine/plugin's
own localization, not authored by the game, so a game localization project
correctly leaves them out — but the exclusion is path-based, not content-based.

**Coverage:** this corpus exercises LOCRES only. Unreal String Table CSV,
DataTable JSON, and DialogueWave JSON are natively supported but were **not**
present in this extract; the VOIN dialogue `.uasset` assets are UE5.6 and
UAssetAPI 1.0.0 cannot parse them (documented PARTIAL). Coverage for those
surfaces remains validated by fixtures, not real files.

### Unity finalization

- UnityPy helper is inventory-first: heavy binary types (Texture2D/Mesh/
  AudioClip/VideoClip/Shader/AnimationClip/Material/Font/…) are enumerated but
  never deserialized; only TextAsset/MonoBehaviour/ScriptableObject/GameObject
  are read.
- TextAsset payloads are routed by content sniffing to JSON/CSV/XML/YAML/Ink/
  Yarn, so narrative and structured formats reach the correct adapter.
- Validated end-to-end against the real `1000xRESIST` bundle (MonoBehaviour
  tree → entries, source SHA-256 unchanged).

### Unity precision audit (real 1000xRESIST MasterDialogueDatabase)

A real `MasterDialogueDatabase` MonoBehaviour (Dialogue System for Unity /
Pixel Crushers, 6 MB typed tree) was sampled and classified. The generic
structured analyzer produced **68,190 entries** — of which **45,625 were false
positives**: the `title` of every typed custom field (`Name`, `Description`,
`Display Name en/zh/ja/fr/…`) was mis-classified as translatable `Menu` text
(the schema field names repeat for every actor/item/dialogue entry).

Added a dedicated Dialogue System extractor (`extractDialogueSystemDatabase`)
that maps the typed `fields[]` structure correctly:

| Surface | Result (logical entries) |
|---|---|
| `Dialogue Text` (type 0) | **2,083** `Dialogue` entries, speaker+listener mapped from `Actor`/`Conversant` ids |
| `Menu Text` (type 0) | **101** `Choice` entries |
| actor `Display Name` | **87** `CharacterName` entries |
| item `Display Name` | **14** `ItemName` entries |

Context now resolves: **2,184 with speaker, 2,138 with listener, 2,188 with
localeVariants** (the type-4 `Localization` fields collapse into variants, so
~22k raw locale strings become 2,285 logical entries — matching the Unreal/
Godot aggregation model). Schema titles, booleans, file lists, poses, and
sequence strings are skipped.

**Stripped typetree (honest boundary):** UnityPy `read_typetree()` returns
`None` for MonoBehaviours whose type tree was stripped at build time. Those
objects are still enumerated in `manifest.json` (pathId/classId/type) but
produce no typed JSON, hence no entries — a documented silent gap
(inventory-only). This corpus's `MasterDialogueDatabase` had a full type tree,
so it was fully extracted; stripped-tree assets remain UNSUPPORTED for text
without an external type-tree database.

**Coverage:** this corpus exercises MonoBehaviour only. TextAsset (JSON/CSV/
Ink/Yarn/XML/YAML) and Unity Localization String Table JSON are natively
supported and fixture-tested, but the 1000xRESIST bundle carries no separate
TextAsset/Localization-table surfaces to audit against real files.
