# v0.4 Worktree Review

This checkpoint records the implemented v0.4 foundation currently present in the worktree. It is not a release notice.

## Architecture Changes

- The current `.lhproj` model is `LocalizationProjectV3`.
- Editorial workflow metadata is kept at project level in `workflow.entries`, separate from `ParsedLocalizationEntry`.
- Effective status is derived by `getEffectiveEntryWorkflowStatus`: empty translations are `untranslated`; non-empty entries default to `translated` unless explicit metadata exists.
- Core storage and cloud request/response contracts now use V3. The collaboration protocol version remains unchanged.
- Frontend state restores workflow metadata from local files, Cloud Projects, and collaboration snapshots, and serializes it when saving or creating a Cloud Project.

## Migration Behavior

- V1 and V2 project JSON remains accepted.
- V1 and V2 are migrated in memory to V3 with an empty workflow map.
- V3 workflow maps are validated and malformed statuses are rejected.
- Migrated local projects are directed through Save As so the original file is not silently overwritten.
- Cloud GET/load decodes the returned project through the same migration path, allowing existing V2 Cloud records to open.

## Implemented Features

- Workflow statuses: Untranslated, Draft, Translated, Needs Review, and Approved.
- Status counts and Draft/Needs Review/Approved filters.
- Status display in entry indicators and list titles.
- Editing an Approved or Needs Review entry returns it to Draft; clearing text removes redundant workflow metadata.
- Viewer read-only behavior remains enforced by existing frontend and server permission paths.
- Existing token errors and warnings remain independent of editorial workflow status.
- Core metadata helpers now cover normalized project tags, glossary issue detection, deterministic translation-memory matching, and compact project statistics.
- CSV and gettext PO parsers/exporters are registered in the normalized format pipeline.
- The editor now exposes project statistics, tag creation/attachment, glossary management and issue display, TM suggestions with explicit Apply, and bounded bulk selection/status/tag/clear actions.
- Structured search terms (`status:`, `tag:`, and `has:error`/`has:warning`) are parsed centrally while ordinary key/source/translation/context search remains supported.
- Desktop localization import/export recognizes JSON, CSV, and PO; `.lhproj` project save remains separate.
- Cloud assignments, comments, activity history, and revision-checked translation restore now use project-scoped PostgreSQL resources and existing Owner/Editor/Viewer access semantics.
- Cloud project saves, comment creation/resolution, assignments, and activity restore use dedicated transactions; project changes and their activity records commit or roll back together.
- PostgreSQL assignments are authoritative for Cloud projects. Revoking a member deletes that member's assignments in the same transaction; local project metadata may retain local comments but never invents Cloud identities.
- Comment and activity reads are bounded to 100 rows and ordered deterministically; pagination is not yet exposed.
- Cloud save authorization is included in the row-locking predicate, and the revision-checked UPDATE repeats authorization, so viewers and outsiders cannot obtain the writer lock or bypass the write check.
- Cloud create/save requests use a small server-side V3 trust-boundary validator for required project, entry, and workflow shape.
- Backend services have permanent Node built-in test coverage using guarded fake pool/client injection (`NODE_ENV=test` only). Tests record query order, transaction control, rollback, and client release without contacting PostgreSQL.
- Local comments are stored in V3 metadata; Cloud comments are persisted separately and loaded through the Cloud API.
- Conflict review now includes a manual merged value and Apply Merge through the normal collaboration update path.

## Known Limitations

- Thread replies, assignment display for all list rows, and bulk Cloud assignment mutation remain intentionally limited.
- PO support preserves ordinary comments and multiline msgid/msgstr/msgctxt fields; obscure gettext plural/header extensions are not normalized.
- Cloud activity search hydration is bounded to the selected entry in the current UI; the durable project activity endpoint is available for broader panels.
- Disposable PostgreSQL/API smoke testing was not run because no local `psql` or Docker executable was available; production configuration was not used.
- Fake database tests do not validate PostgreSQL SQL parsing or migration execution. Disposable PostgreSQL migration/API E2E remains a release gate.
- Cloud create/save now require V3 payloads; existing V2 Cloud records remain readable and can be upgraded on a later successful save.
- No database migration was added in this slice because workflow metadata is stored inside the existing project JSON envelope.
- Visual responsive and RTL interaction checks remain manual follow-up work.
